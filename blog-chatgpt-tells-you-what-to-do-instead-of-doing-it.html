Why ChatGPT Tells You What to Do Instead of Doing It

Published 2026-11-07 · 11 min read · Prompt Helper Gemini

If you have ever asked ChatGPT for something and received a careful, confident lecture instead of the actual work, you know the failure mode: ChatGPT tells you what to do instead of doing it. The r/ChatGPT thread that named the behaviour is titled "How can I get chatGPT to actually complete the task as opposed to just telling me what to do it". One reply in that thread put the mood exactly: "ChatGPT's new behavior is quite frustrating, but I understand the challenges it faces. Sometimes it helps to provide hypothetical examples, but it's discouraging when it forgets by the next response."

This is not one model's moody week. It is the default failure of every instruction-tuned chat model, and it shows up in three shapes: a plan with no patch, a set of instructions with no command, and a description of a tool with no tool call. One developer described the first shape like this: "instead of running tests, it suddenly started asking me to run the tests and printed instructions how to do so".

The good news is that the fix is not a cleverer question. It is a different shape of request, and it is short enough to paste into any chat box. Below: what the failure actually looks like, why the model defaults to coaching, and the five-part prompt block that turns a request into a deliverable.

What "it tells you how" actually looks like

The phrase covers three separate behaviours, and each one has a different cause. Diagnosing which you are looking at is most of the work, because the fix for one is useless against another.

1. The plan with no output

The model announces, in detail, exactly what it is about to do, and then stops. This is the most common shape and the most demoralising, because the plan is good. A user on the OpenAI community forum described a long-running project thread in which the model "switches from execution mode into explanation/planning mode", and another reply spelled out the sequence precisely: "And then the actual result of the announced and thoroughly explained action is completely missing."

The tell is that the reply contains no object you could paste somewhere. It reads like a summary of work rather than the work.

2. The instruction handed back to you

Here the model does the thinking and returns the last step to you. One Hacker News comment described an assistant that had been applying a patch for hours and then announced that "if you want to run the tests, just paste this instruction into a terminal somewhere". Another user put the frustration more bluntly: "No, I don't need you to write a tmux emulator in bash to test your changes bro, just ask me to run the command."

The tell is an imperative aimed at you rather than an action taken. You are now the execution layer, which is the opposite of what you paid for.

3. The tool described instead of called

On the API side the same behaviour shows up when a model talks about a function rather than invoking it. A developer asked the forum a question that reads like a punchline: "it tells the user about the functions". The function was fully described, the parameters were fully understood, and the call never happened.

Request that invites coaching

"Give me a plan for a six-week launch campaign for our new analytics product. Include what I should do and why, and any steps I might be missing."

What you get: a thorough strategy memo, a channel list, a budget outline, and a schedule skeleton. Nothing you can publish.

Request that names the deliverable

"Produce the finished six-week launch campaign for our new analytics product. Deliver a week-by-week schedule table, the actual post copy for three channels, and the metrics to track. Output the campaign itself, not advice on how to build one."

What you get: a table, three sets of copy, and a metrics list you can paste straight into a spreadsheet.

Why ChatGPT tells you what to do instead of doing it

Explaining is the cheapest output a model can produce. A plan cannot be wrong in a way anyone can check; a finished artifact can. Every instinct of an instruction-tuned model points toward the safe one, and a paragraph that reads like a competent consultant satisfies almost any instruction you gave it. Ask for "something about a launch campaign" and a strategy memo is a completely reasonable response.

There is a second cause, and it is more interesting: the behaviour gets worse as the conversation grows. One developer noticed that the assistant had been running code happily for months, then switched into instruction-printing mode, and observed that the context window was running full at the time. Compacting the conversation restored the old behaviour. That matches what other users report about long threads: the model starts restating the plan, losing earlier constraints, and preferring the narrow safe move because it no longer has the working memory to attempt the broad one.

Two practical consequences follow. First, the fix belongs in the request, not in the interface, because there is no interface setting for "stop coaching". Second, a fresh thread is a genuinely useful debugging step, and it is a much cheaper one than re-prompting the same bloated conversation a fifth time.

The prompting guidance published by the model vendors converges on the same point from a different direction: be specific about the task, the context and the output format, and treat the request as a contract rather than a topic. Anthropic's prompting guidance and OpenAI's prompt engineering guide both describe the format instruction as the highest-leverage line in the prompt. A format instruction is also the most direct cure for coaching, because it replaces a topic with a shape.

The fix: name the deliverable, forbid the commentary

Before you reach for a tool, know the shape of the request that works. Everything in this section can be typed by hand in about twenty seconds.

Before — the request that invites a plan Write me a plan for a six-week launch campaign for our new analytics product. Include what I should do and why, and any steps I might be missing. Explain your thinking.
After — the same ask, written as a contract Produce the finished six-week launch campaign for our new analytics product. DELIVERABLE: a week-by-week schedule table with date, channel and owner per row. ASSETS: the actual post copy for three channels, one per channel, each under 90 words. MEASURES: the five metrics to track, each with a target value. RULES: output the campaign only. No preamble, no summary of what you would do, no explanation of why you chose this approach. If a detail is missing, make a reasonable assumption, state it in one line at the end, and continue.

Four things changed. The output is now enumerated, so "complete" has a definition. The artefacts are specified, so there is nothing to advise about. The forbidden material is named, so the preamble has a target. And the permission to assume removes the last excuse for stopping to ask.

The one line that most reliably does the work is the rules block. If you only change one thing, change that one. A model told what not to do has a constraint to satisfy; a model merely told what to do still has to decide how much to say.

Five fixes that survive contact with a real model

1. Ask for the object, not the topic

"Tell me about onboarding" produces an essay about onboarding. "Give me the five screens of the onboarding flow, each with its heading, its body copy and one button label" produces five screens. The difference is whether there is a noun in your request that can be counted.

2. Write the prohibition as a rule, not a complaint

Users report trying "just do it" and getting more coaching. A complaint states a preference; a rule states a constraint. "Output the deliverable only. No preamble, no explanation of your approach, no questions back to me" is a rule, and it is checkable. One forum user found the same in a different register: the working instruction reads "output format: brief, answer only, avoid AI commentary, don't ask for more user questions".

3. Grant the authority to assume

Coaching is often a form of hedging. If the model believes a wrong guess costs more than a question, it asks. Remove that belief by naming who accepts the risk: make a reasonable assumption, state it in one line, and continue. Users who adopted this rule report it works better than any wording that tries to forbid questions, because it gives the model permission rather than taking permission away.

4. Keep the brief short

The opposite of coaching is not a longer prompt. Users testing this found that "for me, a very terse but clear set of 30 lines performed better than providing examples and more nuanced explanations". Thirty lines is enough to hold a deliverable, a format and a set of rules. Every extra paragraph is another chance to dilute the instruction that matters.

5. Start a fresh thread when the thread gets heavy

If the model has begun restating the plan, restating your constraints and generally narrating instead of producing, the context is probably the cause. Compact the conversation or open a new one, restate the goal in one paragraph, and paste the deliverable spec. This costs one message and regularly beats three more rounds of re-prompting in a thread that is already three hundred messages deep.

What actually changes the behaviour

  • Name the artifact. A countable noun is the difference between a plan and a result.
  • Ban the preamble explicitly. A rule beats a complaint because it can be satisfied.
  • Say the output format. Vendor prompting guidance treats this as the highest-leverage line.
  • Grant permission to assume. Hedge-removal beats question-banning.
  • Keep it to about thirty lines, and start a fresh thread once the model starts narrating.

Frequently asked questions

Why does ChatGPT explain the task instead of doing it?

Because a plan is the safest output. Describing a task costs the model nothing, and a plan reads like competence, so it optimises for text that cannot be wrong. Naming the artifact and the format forces a result instead. Ask for a deliverable rather than guidance and the model has an artifact to produce, not a topic to describe.

How do I make ChatGPT do the work instead of giving me instructions?

Name the artifact and forbid the commentary. Ask for the finished table, the actual code, the real email, and add one line such as no preamble, no explanation of what you would do, output only the deliverable. Also say what to do when something is missing. Vague requests invite guidance; specific requests with an explicit format produce output.

Does telling ChatGPT to 'just do it' actually work?

Rarely on its own. Just do it states a preference but leaves the decision to the model, and a model that thinks a question is safer keeps asking. What works is transferring authority: make assumptions, state them in one line, and proceed. Pair that with a deliverable and an output contract, and coaching mode has nowhere left to go.

Why does ChatGPT ask me to run the command instead of running it?

Two reasons. The model has drifted into explaining rather than acting, so it hands the step back to you. And a long conversation can push it into a degraded band where caution wins. The fix: restate the action as the deliverable, keep the brief short, and start a fresh thread once it has grown long.

Does the same fix work on Claude, Gemini, and other chat models?

Yes. The coaching behaviour is a property of instruction-tuned models rather than one vendor, and the fix sits in the request rather than the interface. Ask for the artifact, forbid preamble, state the format, and grant permission to assume. The one vendor-specific variable is how much padding you accept by default, since models differ in how much they pad.

How do I stop ChatGPT describing a function instead of calling it?

Say the requirement instead of assuming it. State that the action must be taken rather than discussed, and make the trigger part of the request, for example always update the record rather than explain how to update it. When the action has a set of inputs, name the fields you expect back. A described function is a missing result.

The bottom line: ask for the artifact, not the advice

None of this is a trick about hidden settings or a magic phrase. When ChatGPT tells you what to do instead of doing it, the request has left the door open for a plan, and a plan is always a respectable answer to a question about a topic. Close the door by naming the object you want, naming its format, forbidding the preamble in the rules block, and letting the model assume rather than ask. The users who cracked this did it with a rule, not a wish: "So when you give me a task, don't tell me how to do it." That is a contract. And once you have the contract, the same rough sentence you already type every morning can carry it for you.
